## Головне рішення на старті: чи потрібна оплата Pro в застосунку одразу?

У тебе **два монетизаційні канали**: LiqPay на вебі (працює) і store-білінг (IAP) через
RevenueCat на телефонах. За правилами Apple/Google в нативному застосунку не можна
показувати зовнішню оплату (LiqPay) — тільки IAP. Тому є два шляхи для **першого** релізу:

| | **Шлях A — швидкий (рекомендую)** | **Шлях B — повний** |
|---|---|---|
| Що | v1 БЕЗ оплати в застосунку. Pro керується на вебі (otutorhub.com). У телефоні картка покупки просто не показується. | v1 одразу з покупкою Pro через IAP. |
| Налаштувань | Нуль про RevenueCat/продукти/вебхук. | RevenueCat + продукти в обох сторах + вебхук + пісочниця. |
| Час до сторів | На тижні швидше. | +1–2 тижні консольної роботи. |
| Ризик реджекту | Низький (немає зовнішніх посилань на оплату — LiqPay сховано; кнопки-пустишки теж немає). | Середній (усе має ідеально співпасти, інакше «покупка не працює» = реджект). |

✅ **зроблено в коді:** нативна картка покупки тепер **сама ховається**, якщо продукти IAP
ще не налаштовані ([SubscriptionPage.tsx:380](../src/pages/SubscriptionPage.tsx#L380)) — тож
Шлях A безпечний: жодної «мертвої» кнопки. Коли/якщо налаштуєш продукти в RevenueCat —
картка зʼявиться сама, код міняти не треба.

**Рекомендація:** роби **Шлях A** для v1 (розділи 1–7 нижче), а весь блок RevenueCat
(розділ 8) винеси в v1.1 — саме так і планувалося спочатку. Нижче все розписано в
порядку залежностей; блок 8 можеш пропустити для першого релізу.

## 3. Перевірити видалення акаунта (вимога обох сторів)

Функція видалення **вже є в коді й розгорнута** (кнопка в Профілі → «Небезпечна зона» →
«Видалити акаунт» → edge-функція `delete-account` → RPC `purge_user_data` → видалення auth-юзера).
Apple 5.1.1(v) і Google вимагають, щоб видалення було **всередині застосунку** і реально
видаляло акаунт. Перевір **на тестовому акаунті** (НЕ на своєму):

1. Спершу переконайся, що функція жива: Supabase → Edge Functions → має бути `delete-account`
   зі свіжою датою. Якщо немає — попроси Lovable її задеплоїти. **Це критично**: якщо кнопка
   кине помилку під час рев'ю — Apple відхилить.
2. Зареєструй новий акаунт репетитора на запасний email.
3. Профіль → «Небезпечна зона» → «Видалити акаунт» → підтвердь.
4. Очікування: тост «Акаунт видалено», вихід, редірект на лендинг.
5. **Доказ, що спрацювало:** спробуй увійти тим самим email — вхід має ПРОВАЛИТИСЬ; спробуй
   зареєструватись знову тим самим email — має ВДАТИСЬ (email звільнився).
6. Повтори те саме для акаунта **учня** (у нього окремий шлях `/student/profile`).

> ⚠️ Видалення акаунта **не** скасовує авто-підписку в App Store/Play — вона живе в
> Apple/Google ID. Це нормально; просто в нотатках рев'юеру напиши, що підписка керується
> в сторі. І дай рев'юеру **окремий одноразовий акаунт**, який не шкода видалити (не основний демо).

## 5. Android → Google Play (почни з нього — простіше, Mac НЕ потрібен)

**Стан коду:** нативний Android-проєкт уже є (`android/`), `appId = ua.otutorhub.app`,
targetSdk 36 (відповідає вимогам Play). 

✅ **зроблено в коді:** я під'єднав **release-підпис** у [android/app/build.gradle](../android/app/build.gradle)
(читає ключ із `android/key.properties`, який git-ігнорується), і захистив keystore від
випадкового коміту в `.gitignore`. Тобі лишається лише згенерувати ключ і заповнити файл.

**Одноразово — створити upload-keystore** (у терміналі; на будь-якій ОС з Java):
```bash
keytool -genkey -v -keystore ~/keys/otutorhub-upload.jks \
  -keyalias otutorhub -keyalg RSA -keysize 2048 -validity 10000
```
- Придумай і **надійно збережи** паролі (менеджер паролів). **Втрата `.jks` = неможливість
  оновлювати застосунок** (якщо не увімкнеш Play App Signing — увімкни його при першому
  завантаженні, це рятує від втрати ключа).
- Тримай `.jks` **поза репо** (напр. `~/keys/`), зроби бекап у хмару.

**Заповнити ключі для збірки** — скопіюй шаблон і встав реальні значення:
```bash
cp android/key.properties.example android/key.properties
# відредагуй android/key.properties: storeFile (абсолютний шлях до .jks), паролі, alias
```
(Файл `android/key.properties` git-ігнорується — не потрапить у репо.)

**Environment для збірки** — `.env.production` (Vite вбудовує змінні під час білду):
```bash
cp .env.production.example .env.production
# впиши VITE_SUPABASE_* (є в прикладі). VITE_REVENUECAT_ANDROID_KEY лиши порожнім для Шляху A.
```

**Зібрати підписаний .aab** (Play приймає **.aab**, не .apk):
```bash
npm run build
npx cap sync android
cd android && ./gradlew bundleRelease
# готовий файл: android/app/build/outputs/bundle/release/app-release.aab
```

**У Google Play Console** (акаунт розробника — одноразово $25):
1. Створи застосунок → завантаж `.aab` у internal testing (спершу), потім production.
2. Заповни **Data Safety** форму — див. розділ 9 (Приватність) нижче.
3. Store listing: назва/опис/іконка 512/feature graphic 1024×500/скріншоти.
4. Content rating анкету, target audience (18+), privacy URL.
5. Кожне наступне завантаження — **підвищуй `versionCode`** у `android/app/build.gradle`
   (зараз 1 — для першого релізу ок; для другого став 2, і т.д.).

**Стан коду:** папки `ios/` ще немає (правильно — її треба згенерувати на Mac).
`capacitor.config.ts` чистий (без dev-URL). Детальний покроковий гайд уже є —

**Одноразово треба:** Mac + Xcode (свіжий), **Apple Developer Program** ($99/рік),

**Створити iOS-проєкт:**
```bash
npm i @capacitor/ios@^8.4.0        # версія має збігатися з @capacitor/core (8.4.0)
npx cap add ios
npm run build && npx cap sync ios
npx cap open ios                    # відкриє Xcode
```
**У Xcode:** Signing & Capabilities → обери свою **Team**; переконайся, що Bundle Identifier =
`ua.otutorhub.app`; лиши автоматичне керування профілем. Далі: Product → Archive →
Distribute → App Store Connect.

**У App Store Connect** (браузер): створи застосунок (Bundle ID `ua.otutorhub.app`), завантаж
білд, заповни **App Privacy** (розділ 9), скріншоти 6.7″, опис, privacy URL, віковий рейтинг,
демо-акаунт у нотатках рев'ю.

> Для Шляху A (v1 без IAP) в App Store Connect **не** створюй продукти-підписки — картка
> покупки в застосунку не показується, зовнішніх посилань на оплату немає. Якщо рев'юер
> спитає про Pro — це кросплатформна опція, застосунок повністю робочий на Free.

## 8. (v1.1) Оплата Pro через IAP — RevenueCat

Роби це **тільки якщо** обрала Шлях B, або пізніше в v1.1. Код готовий; лишається консольне
налаштування. Ключове, що має **точно** співпасти з кодом:
- **Entitlement id = `pro`** (рівно так, малими) — код перевіряє саме цей рядок

  Тому **id продуктів можуть бути будь-якими** (у старих доках `pro_monthly`/`pro_yearly`

**Кроки:**
1. **App Store Connect / Play Console:** створи авто-поновлювані підписки (місячна + за

2. **RevenueCat:** проєкт → додай і App Store, і Play застосунки (обидва `ua.otutorhub.app`);
   Entitlement `pro`; Offering (current) з пакетами Monthly+Annual; прив'яжи продукти сторів
   до цих пакетів і до entitlement `pro`.
3. **Ключі SDK у білд:** `VITE_REVENUECAT_IOS_KEY` (`appl_…`) і `VITE_REVENUECAT_ANDROID_KEY`

4. **Вебхук:** попроси Lovable задеплоїти edge-функцію `revenuecat-webhook`; у Supabase →
   Edge Functions → Secrets постав `REVENUECAT_WEBHOOK_SECRET` = випадковий рядок
   (`openssl rand -hex 32`).
5. **RevenueCat → Integrations → Webhooks:** URL =
   `https://kficbcjqcbhqhjimxfed.supabase.co/functions/v1/revenuecat-webhook`, заголовок
   Authorization = `Bearer <той самий REVENUECAT_WEBHOOK_SECRET>` (рівно, без зайвого пробілу/

6. **Тест у пісочниці** (iOS Sandbox / Play test): купи місячну, купи річну, Restore, Cancel —

> LiqPay має лишатись **прихованою** в нативі — не додавай зовнішніх посилань на оплату

## 9. Приватність — форми Apple App Privacy + Google Play Data Safety

Застосунок акаунт-орієнтований, тож усі дані **пов'язані з особою** (Supabase `user.id`).
✅ Повна Politika приватності вже є в застосунку (`/privacy`), і Microsoft Clarity
(аналітика) вмикається **лише після згоди** (банер cookie) — це GDPR-friendly.

**Що задекларувати (обидві форми):**
- **Контакти/ідентифікатори:** ім'я, email, телефон, user id. (+ контакти учнів, які вводить репетитор — це User Content про інших.)
- **Контент користувача:** аватар, вкладення в чаті й уроках, нотатки/домашки; **аудіо** — лише якщо ввімкнеш Fireflies-запис уроків.
- **Фінанси:** тільки суми/статуси оплат — **картки НЕ зберігаються** (їх обробляють LiqPay/стори). Так і вкажи: card data NOT collected.
- **Покупки:** історія покупок через RevenueCat (пов'язана з user id).
- **Аналітика/діагностика:** Microsoft Clarity — признач ціль **Analytics**, а на питання
  «Use for tracking?» → **NO** (не ділиться з рекламними мережами) ⇒ ATT-запит Apple не потрібен.
  Признач як **optional** (користувач може відмовитись).
- **Шифрування в передачі:** YES. **Видалення за запитом:** YES (є `delete-account`).
- **Треті сторони (processors):** LiqPay/PrivatBank, Microsoft/Clarity, Telegram (opt-in),
  RevenueCat (якщо IAP). Дані **не продаються**, не йдуть у рекламу.

**Застереження:**
- Push-токени: нативний FCM/APNs **ще не під'єднаний** (`google-services.json` немає). Тому
  **не** декларуй збір push-токенів у нативі, поки push реально не ввімкнено (інакше — невідповідність форми).
- Google Calendar (opt-in) просить scope `calendar.events` — для проду може знадобитись
  окрема **Google OAuth verification** (не пов'язана зі сторами); екран згоди має вести на цю ж політику.
- Додай **RevenueCat** і (якщо ввімкнеш) **Fireflies** у текст політики `/privacy` перед
  сабмітом — зараз вони там не названі явно, а форма має збігатися з політикою.
